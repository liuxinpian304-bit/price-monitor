# 桌面采集价格与通知安全补救设计

日期：2026-08-26
状态：已确认，待实施
适用范围：淘宝桌面采集器、采集报告 API、企业微信通知批次

## 1. 背景

桌面采集试点的最终代码复审仍有两个会阻止真实上线的问题：

1. 旧采集数据中的 `includedInActivityPrice: false` 不能证明公开优惠未包含在活动价中。若继续按“未包含”处理，系统可能重复扣减优惠，产生错误的 `CONFIRMED` 低价。
2. 当前流程先提交价格告警，再创建企业微信通知批次。进程若在两步之间退出，重试会因告警去重而得不到本次新告警，导致通知永久丢失。

本补救设计只解决这两个问题，不扩展采集范围、不改变后台界面，也不执行真实淘宝或企业微信操作。

## 2. 已确认的业务决策

- 新数据必须明确公开优惠与活动价的关系：`INCLUDED`、`EXCLUDED` 或 `UNKNOWN`。
- 只有页面证据明确为 `EXCLUDED` 时，公开优惠才能从活动价中再次扣减。
- 旧数据中缺失三态字段，或只有旧的 `includedInActivityPrice: false`，统一解释为 `UNKNOWN`。
- 旧记录保留，但受影响的 SKU 统一降为人工复核，不参与自动低价提醒。
- 旧检查点保留采集进度；加载时进行保守迁移，不要求整次任务从头开始。
- 价格告警和待发送通知批次必须在同一个数据库事务内提交。
- 企业微信响应结果不明确时，继续保持“不自动重复发送”的现有策略。

## 3. 方案比较

### 3.1 采用：保守兼容迁移与事务型通知发件箱

旧记录在读取边界转换为三态数据，并重新计算价格置信度。告警评估事务同时保存价格告警和通知批次。该方案保留进度，同时关闭误报和漏报两个故障窗口。

### 3.2 未采用：废弃全部旧检查点

提升数据契约版本并拒绝所有旧文件可以减少迁移代码，但会丢失已完成的商品和 SKU 进度，运营上需要重新采集整个任务。

### 3.3 未采用：事后查询告警补建通知

重启后按快照反查告警可以缩小改动，但仍需要推断某条去重告警属于哪次通知，故障边界和审计语义不如事务型发件箱明确。

## 4. 价格证据设计

### 4.1 契约归一化

采集报告输入继续兼容旧字段，但解析后的标准类型必须始终包含 `activityPriceInclusion`：

- 显式三态字段存在时，使用其值。
- 三态字段缺失且旧布尔值为 `true` 时，归一化为 `INCLUDED`。
- 三态字段缺失且旧布尔值为 `false` 时，归一化为 `UNKNOWN`，不得推断为 `EXCLUDED`。

新生成的报告必须显式写入三态字段。旧布尔字段只作为兼容输入，不再作为“优惠未包含”的充分证据。

### 4.2 价格计算

共享公开价格计算器只接受归一化后的三态含义：

- `INCLUDED`：不重复扣减。
- `EXCLUDED`：满足门槛且金额、叠加组等证据完整时可以扣减。
- `UNKNOWN`：记录人工复核原因；没有页面官方预估到手价时，`payableFen` 为 `null`，置信度为 `MANUAL_REVIEW`。
- 若页面提供独立的官方预估到手价，可以保留为 `ESTIMATED`，但仍不触发确定性低价告警。

### 4.3 报告边界防线

采集报告契约必须拒绝以下组合：

- 任一适用的公开优惠为 `UNKNOWN`，但 SKU 声称 `priceConfidence: CONFIRMED`。
- 三态字段缺失的旧公开优惠被当成明确 `EXCLUDED` 后形成的 `CONFIRMED` 价格。
- `CONFIRMED` 的价格组件与应付价算术不一致。

API 只持久化通过该边界校验的报告，因此即使出现非官方采集器或损坏文件，也不能把不确定优惠送入自动告警。

### 4.4 旧检查点迁移

检查点存储在正式契约校验前执行一次纯数据迁移：

1. 归一化每条旧优惠的三态字段。
2. 对包含 `UNKNOWN` 公开优惠的 SKU 重新运行共享价格计算器。
3. 覆盖折扣组件、`payableFen` 和 `priceConfidence`，确保结果为 `MANUAL_REVIEW` 或 `ESTIMATED`，绝不保留 `CONFIRMED`。
4. 保留商品、SKU、排名、证据引用和完成进度。
5. 下次原子保存检查点时写回归一化后的安全格式。

迁移必须幂等。重复加载同一检查点不能继续改变金额、置信度或完成进度。

## 5. 原子通知批次设计

### 5.1 事务边界

`RunAlertService.evaluateRun()` 已在单个数据库事务中执行快照匹配和价格告警去重。本次补救把通知批次创建也放入该事务：

1. 锁定本次 `CollectionRun`。
2. 保存快照和候选匹配结果。
3. 选择唯一我方基准并创建本次新价格告警。
4. 构建不可变的 `RunAlertSummary`。
5. 当摘要包含新告警或系统问题时，以 `collectionRunId` 为唯一键创建 `RunAlertNotificationBatch`。
6. 告警、摘要和通知批次一起提交。

事务提交前崩溃时，上述写入全部回滚，评估可以安全重试。事务提交后崩溃时，通知批次已经存在，后台协调器可以继续发送。

### 5.2 发送与恢复

通知器只认领已经持久化的批次，不再负责为正常评估流程临时创建批次。批次中的摘要和告警 ID 是本次发送的唯一事实来源。

启动及每 30 秒运行的协调器继续处理：

- `PENDING`：可认领并发送。
- `SENDING` 且租约仍有效：不并发发送。
- `SENDING` 且租约过期：标记为 `AMBIGUOUS`，不盲目重发。
- 明确发送失败：沿用现有有限重试次数。
- `NOTIFIED`、`AMBIGUOUS` 或最终 `FAILED`：不再次认领。

同一 `collectionRunId` 只能有一个通知批次。评估重试不得覆盖首次提交的不可变摘要，也不得产生第二条企业微信消息。

### 5.3 基准缺失提醒

我方基准缺失或歧义仍属于系统问题。即使没有价格告警，也必须在评估事务内创建通知批次，确保该系统提醒同样具备崩溃恢复能力。

## 6. 数据模型与兼容性

- 复用现有 `RunAlertNotificationBatch`，不新增第二套发件箱表。
- `collectionRunId` 的现有唯一约束继续提供幂等性。
- 通知摘要继续作为 JSON 保存，并通过现有严格 schema 读取。
- 如实现需要新增状态或字段，迁移必须向后兼容，不得删除现有告警和批次。
- 旧数据库中已经存在的 `PENDING`、`SENDING`、`AMBIGUOUS`、`FAILED` 和 `NOTIFIED` 批次保持原语义。

## 7. 错误处理

- 旧检查点无法安全迁移时，返回固定且脱敏的“检查点不兼容，需要重新采集”错误，不上传部分可信的价格。
- 通知批次无法在评估事务内写入时，整个评估事务回滚；不得只保存价格告警。
- 事务已提交但发送失败时，只更新通知批次状态，不删除告警或摘要。
- 企业微信响应丢失继续标记 `AMBIGUOUS`，由运营人工确认，不自动重复 POST。

## 8. 测试设计

实施必须先添加失败测试，再修改生产代码。

### 8.1 价格测试

- 旧的 `includedInActivityPrice: false` 归一化为 `UNKNOWN`，不能计算出 `CONFIRMED`。
- 旧检查点保留采集进度，同时把受影响 SKU 降为人工复核。
- 旧检查点迁移重复执行两次结果完全一致。
- 显式 `EXCLUDED` 且证据完整时仍能产生正确的 `CONFIRMED` 到手价。
- 显式 `INCLUDED` 不重复扣减。
- API 契约拒绝“公开优惠归属不明 + CONFIRMED”的报告。

### 8.2 通知测试

- 数据库集成测试模拟评估事务提交后、通知发送前进程退出，确认通知批次已经存在。
- 重建协调器后能从该批次发送一次，并更新关联告警。
- 同一次运行重复评估不能覆盖摘要或创建第二批次。
- 事务内通知批次写入失败时，价格告警同时回滚。
- 基准缺失系统提醒在相同崩溃边界下仍可恢复。
- 企业微信响应不明确时保持 `AMBIGUOUS` 且不重复发送。

### 8.3 回归门槛

- 价格、契约、检查点、API 告警和通知的聚焦测试全部通过。
- PostgreSQL 集成测试在隔离 schema 中通过。
- 完整 `pnpm verify`、浏览器回归、公开仓库审计、Prisma 校验和迁移状态通过。
- macOS Swift 助手继续能够构建；完整 XCTest 仍需具备完整 Xcode 的主机。

## 9. 上线与真实验收边界

本补救代码通过自动化和独立复审后，才恢复原试点的现场验收顺序：

1. 在完整 Xcode 环境运行 Swift XCTest。
2. 管理员在场时运行 3 个搜索结果的小规模淘宝采集。
3. 验证前 50 个结果或明确 `END_MARKER`。
4. 展示待发送企业微信内容，取得当次明确确认后只发送一条真实消息。

任何自动化测试都不能替代上述真实操作确认。本设计本身不授权访问淘宝账号或发送企业微信消息。

## 10. 完成标准

以下条件全部满足后，本补救任务才算完成：

- 不明确的公开优惠无法形成 `CONFIRMED` 自动告警。
- 旧检查点可以保留进度并安全降级，且迁移幂等。
- 每个需要通知的运行在告警事务提交时已经拥有持久通知批次。
- 任意进程退出点都不会形成“告警已保存但永远没有通知批次”的状态。
- 重启恢复不会重复发送企业微信消息。
- 聚焦测试、数据库集成测试、完整自动化验证和独立代码复审均通过。
- 真实淘宝与企业微信操作仍保持人工确认门槛。
