# 淘宝前 50 店铺价盘与 SKU 缺口报告设计

日期：2026-08-26
状态：设计方向已确认，待文档复核后实施
第一期平台：淘宝、天猫桌面版
我方店铺：星空乐器专营店
提醒渠道：企业微信运营群

## 1. 文档关系与本次变更

本设计扩展《淘宝桌面版全 SKU 比价采集设计》（2026-08-24），继续沿用其中的桌面采集、前 50 个搜索位置、全 SKU 遍历、公开活动到手价、人工改价和不绕过平台验证等原则。

本次明确替换旧设计中的“每个监控型号只选择一个我方目标 SKU 作为统一基准”语义。新规则是：

- 每次运行先采集该型号下全部已配置的我方商品链接和全部有效 SKU。
- 系统为每个可确认的 SKU 组合生成稳定的组合签名。
- 每一个同行 SKU 只与签名完全相同的我方 SKU 比较。
- 我方同一组合存在多个链接或 SKU 时，使用本次运行中最低的已确认单件到手价作为该组合基准，同时保留其他我方链接供审计。
- 同行组合在我方不存在时进入“我方缺失组合”，不产生低价告警。

`CollectionRun.ownBaselineSnapshotId` 只保留为旧接口兼容字段，不再是比价结论的权威依据。每条同行 SKU 的 `comparisonOwnSnapshotId` 才是实际采用的我方基准。

## 2. 目标

对运营输入的型号执行一次可审计的淘宝价盘采集：

1. 按淘宝当前展示顺序读取前 50 个搜索位置。
2. 打开对应商品并读取页面可访问的全部有效 SKU、库存、活动和预计单件到手价。
3. 按店铺整理前 50 价盘，同时保留每一个原始排名和链接。
4. 对完全相同的商品、型号、成色、数量和核心配置进行逐组合比价。
5. 只要同行确认到手价低于我方同组合最低确认价，即使仅低 `0.01` 元，也生成低价结果。
6. 单独列出同行有、我方没有的 SKU 组合，帮助运营补充商品组合。
7. 每次运行向企业微信运营群发送一条摘要，价格修改仍由运营人工完成。

## 3. 非目标

- 不自动修改淘宝、天猫或 ERP 中的价格。
- 不把“前 50”解释为 50 家不同店铺；它始终表示 50 个搜索展示位置。
- 不绕过登录验证、验证码、滑块、访问限制或平台风控。
- 不读取、导出或提交淘宝 Cookie、密码、会话令牌等凭据。
- 不用错误型号、二手、样机、租赁、定金、单独配件或信息不完整的 SKU 产生低价告警。
- 不把赠品、远程调试、安装服务等主观价值折算为现金价格。
- 第一阶段不实现其他电商平台，也不建立自动调价闭环。

## 4. 核心定义

### 4.1 前 50 个搜索位置

- 从搜索结果顶部开始，按页面展示顺序编号 `1..50`。
- 普通结果与明确标记的推广结果都占一个位置，并保存推广标记。
- 同一商品重复出现时保留每个排名位置，但详情页只采集一次；报告中该商品显示全部排名。
- 只有读取到 50 个位置，或页面出现可验证的“没有更多结果”结束标记，搜索阶段才算完整。
- 登录失效、平台验证、滚动加载异常或界面结构变化导致少于 50 个位置时，不得把运行标为完整成功。

### 4.2 按店铺价盘

“按店铺”是报告展示分组，不改变搜索位置口径。店铺组内保留：

- 店铺名称、最早排名和全部出现排名。
- 商品标题、完整链接、商品标识和推广标记。
- 所有已读取 SKU 的规格、组合构成、库存、活动、确认价格和证据状态。
- 对应我方同组合最低价格、我方链接、差价和判断结果。

默认按店铺最早出现排名升序排列，店铺内按商品最早排名、SKU 到手价和 SKU 标识稳定排序。

### 4.3 完全相同组合

只有以下信息均可确认且一致时，同行 SKU 与我方 SKU 才属于同一组合：

- 品牌和标准型号。
- 新品、二手、样机等成色。
- 核心产品型号和数量。
- 需要付费才能获得的主要配件型号与数量。
- 对该监控型号有实质影响的区域版本、保修类型或其他已配置属性。
- 当监控规则启用 `colorComparable` 时，颜色也必须一致；未启用时颜色仅展示，不影响组合签名。

同一主型号但核心部件、数量或付费套装不同，不允许直接互相比价。

### 4.4 我方缺失组合

同行 SKU 的型号和组合构成能够被完整确认，但所有本次有效我方 SKU 中不存在相同组合签名时，状态为 `MISSING_OWN`。

该状态是选品和上架信息，不是低价结论：

- 不创建 `PriceAlert`。
- 不显示“同行低于我方”。
- 不作为采集故障写入 `CollectionIssue`。
- 报告显示同行店铺、最低确认价、首次排名、链接和完整组合。

如果我方链接采集不完整、同行组合包含未知部件或价格无法确认，进入 `REVIEW`，不能武断标记为缺失。

## 5. 总体数据流

一次运行按以下顺序执行：

1. **运行前检查**：确认淘宝桌面版已登录、辅助功能可用、全部启用的我方链接可访问。
2. **我方目录采集**：遍历该型号下全部已配置我方链接和全部有效 SKU。
3. **搜索位置采集**：搜索型号并建立前 50 个位置清单，保留重复商品位置。
4. **同行详情采集**：按唯一商品访问详情页，遍历全部可选有效 SKU。
5. **标准化**：解析品牌、型号、成色、数量、结构化部件、活动、库存和价格置信度。
6. **组合签名**：为可确认组合生成稳定签名，建立我方组合基准索引。
7. **逐 SKU 评价**：同行 SKU 分为 `MATCHED`、`MISSING_OWN`、`REVIEW` 或 `EXCLUDED`。
8. **告警计算**：只对 `MATCHED` 且双方价格均确认、均可售的 SKU 比较价格。
9. **报告聚合**：生成按店铺价盘、确认低价和我方缺失组合三类结果。
10. **通知批次**：保存一条幂等的企业微信摘要批次，人工确认首次真实发送后再投递。

采集器只负责读取和提交事实；标准化、比价、分组、告警和通知全部由 API 服务完成，Mac 与 Windows 共用同一业务逻辑。

## 6. SKU 部件模型

采集契约中的每个结构化部件必须带有角色、标准名称、型号、数量和解析依据。角色固定为：

- `CORE`：被监控的核心产品，例如 NT1S 麦克风本体或 MDR-7506 耳机。
- `PAID_ACCESSORY`：SKU 价格中包含、且会改变套装价值的付费主要配件，例如指定型号支架、声卡或第二只麦克风。
- `GIFT_OR_SERVICE`：赠品、线材赠送、驱动安装、远程调试、保养等，不进入组合签名，但完整展示。
- `UNKNOWN`：无法判断角色、型号或数量的内容。任一可能影响配置的部件为 `UNKNOWN` 时，该 SKU 必须进入人工复核。

通用小赠品和服务不能为了凑齐套装而被归入 `PAID_ACCESSORY`。付费配件缺少明确型号或数量时也不能自动视为同款。

## 7. 组合规范化与签名

系统先生成规范化对象，再计算签名。规范化对象使用固定字段和排序：

```json
{
  "version": "sku-combination-v1",
  "brand": "rode",
  "model": "nt1s",
  "condition": "new",
  "core": [
    { "model": "nt1s", "quantity": 1 }
  ],
  "paidAccessories": [],
  "materialAttributes": {},
  "color": null
}
```

规则如下：

- 文本先经过大小写、全半角、空白、品牌别名和型号别名规范化。
- `core` 与 `paidAccessories` 按标准型号、数量稳定排序，输入顺序不影响结果。
- `GIFT_OR_SERVICE` 不进入对象；它只影响报告说明。
- 区域版本、保修类型等只有在监控规则声明为实质属性时写入 `materialAttributes`。
- 颜色仅在 `colorComparable=true` 时写入，否则为 `null`。
- 任何必需字段不确定时不生成签名，直接进入 `REVIEW`。

签名格式为：

```text
sku-combination-v1:<sha256(canonical-json)>
```

同时保存可读的 `combinationLabel`，例如“RODE NT1S 新品 单只麦克风”或“Sony MDR-7506 新品 1 件 + 指定型号耳放 1 台”。业务判断使用签名，可读标签只用于展示。

## 8. 我方多基准索引

我方基准只来自该监控型号下启用并成功采集的 `OwnListing`。搜索结果中识别到星空乐器专营店时保留排名，并在商品标识一致时关联已配置链接；仅凭店铺名称发现但尚未配置的商品不自动成为价格基准。

一个我方 SKU 只有同时满足以下条件才进入基准索引：

- 商品和 SKU 属于目标标准型号。
- 组合签名可确认。
- 库存为 `IN_STOCK`。
- 预计单件到手价存在且 `priceConfidence=CONFIRMED`。
- 不是二手、样机、租赁、定金、单独配件或下架商品。

索引结构为 `combinationSignature -> OwnBaseline[]`。每个签名按以下顺序选择权威基准：

1. `payableFen` 最低。
2. `platformItemId` 字典序靠前。
3. `skuId` 字典序靠前。
4. `OfferSnapshot.id` 字典序靠前。

所有其他同组合我方 SKU 继续保留为 `alternativeOwnSnapshots`。报告必须让运营看到系统用了哪个最低价，也能展开其他我方链接。

若同签名只存在我方无库存 SKU，同行结果归入 `MISSING_OWN`，原因写为 `OWN_OUT_OF_STOCK_ONLY`；报告明确显示“我方有该组合但当前无库存”。若我方同签名存在 SKU 但价格不确定，则同行结果进入 `REVIEW`，原因写为 `OWN_PRICE_UNCONFIRMED`。

只要任一启用我方链接采集失败，本次运行的“缺失组合”结论整体降级为 `REVIEW`，原因写为 `OWN_CATALOG_INCOMPLETE`，避免把采集失败误报成我方没有。

## 9. 同行 SKU 评价规则

评价分两层进行：

### 9.1 商品级门槛

- 品牌或标准型号明确不同：`EXCLUDED`。
- 二手、样机、租赁、定金、维修、空盒、单独配件：`EXCLUDED`。
- 主型号可能相同但信息不足：`REVIEW`。
- 通过商品级门槛后才进入组合评价。

### 9.2 组合级状态

- `OWN`：符合条件的我方 SKU。
- `MATCHED`：同行签名在我方索引中存在，且已绑定选中的最低价我方快照。
- `MISSING_OWN`：同行组合可确认，但我方索引中没有可售同签名组合。
- `REVIEW`：型号、部件、数量、活动、库存或我方目录完整性不足。
- `EXCLUDED`：明确不属于目标商品或不具备可比性。

只有以下表达式为真时才创建确认低价告警：

```text
state = MATCHED
AND competitor.stockState = IN_STOCK
AND competitor.priceConfidence = CONFIRMED
AND own.priceConfidence = CONFIRMED
AND competitor.payableFen < own.payableFen
```

差价计算为 `own.payableFen - competitor.payableFen`，最小触发差价为 `1` 分。价格相同或更高不告警，但仍显示在价盘中。

## 10. 价格与活动口径

延续既有价格规则：

```text
预计单件到手价 = 活动价 - 可确定且单件可用的公开优惠 + 必付费用
```

- 我方和同行使用完全相同的计算方式。
- 单件未达到门槛的满减、必须凑单的优惠、会员专享、个人红包和私聊客服价不直接扣减。
- 页面明确展示的平台立减、店铺券或单件满减可以按叠加规则计算。
- 每次 SKU 选择后必须等待 SKU、价格和活动区域稳定，再读取价格。
- 页面价格持续变化时标记 `PRICE_UNSTABLE`，保留多次读数并进入 `REVIEW`。
- 搜索卡片价只作为发现证据，最终判断必须使用已选择 SKU 的详情页价格。

## 11. 数据持久化设计

### 11.1 新增枚举

```prisma
enum SkuCombinationState {
  OWN
  MATCHED
  MISSING_OWN
  REVIEW
  EXCLUDED
}
```

### 11.2 `OfferSnapshot` 新增字段

```prisma
combinationSignature       String?
combinationLabel           String?
combinationState           SkuCombinationState?
combinationReasons         Json?
comparisonOwnSnapshotId    String?
comparisonOwnSnapshot      OfferSnapshot?  @relation("OfferComparisonOwn", fields: [comparisonOwnSnapshotId], references: [id], onDelete: SetNull)
comparedCompetitorSnapshots OfferSnapshot[] @relation("OfferComparisonOwn")
```

`combinationReasons` 使用结构化对象保存规则版本、规范化字段、状态原因代码、缺失原因和被忽略的赠品或服务。它与现有 `matchReasons` 分工明确：`matchReasons` 记录商品和型号识别依据，`combinationReasons` 记录 SKU 组合与基准选择依据。

新增索引：

- `[collectionRunId, combinationState]`
- `[collectionRunId, combinationSignature]`
- `[collectionRunId, shopName]`
- `[comparisonOwnSnapshotId]`

字段均允许为空，以兼容历史运行。新运行完成标准化后必须填充状态；不能用空值代替 `REVIEW`。

### 11.3 现有模型的使用

- `CollectionSearchPosition` 继续作为前 50 原始排名的唯一事实来源。
- `PriceAlert.ownSnapshotId` 指向该同行组合实际选中的最低价我方快照。
- `PriceAlert.competitorSnapshotId` 指向同行 SKU 快照。
- `CollectionRun.ownBaselineSnapshotId` 可写入本次所有我方基准中的全局最低价，用于旧页面兼容，但新逻辑不得据此统一比较全部 SKU。
- `RunAlertNotificationBatch` 保存本次运行唯一的通知摘要和关联告警 ID，保证重试不重复刷屏。
- “我方缺失组合”是正常商业结果，不为每条缺失记录创建 `CollectionIssue`。

告警去重键必须包含监控型号、组合签名、同行商品和 SKU、实际我方快照以及同行到手价。同行价格进一步下降、我方最低基准变化，或恢复后再次低于我方时，可以形成新的有效提醒。

## 12. 报告 API

现有运行详情接口扩展为以下稳定结构，旧字段继续保留：

```text
summary
  searchPositionsRead / searchLimit / terminationReason
  distinctShopCount / distinctItemCount / skuCount
  matchedSkuCount / confirmedLowCount
  missingCombinationCount / reviewCount / excludedCount

priceBoard.shops[]
  shopName / earliestRank / ranks / positionCount
  itemCount / skuCount / confirmedLowCount / missingCombinationCount
  items[].positions[]
  items[].skus[]

confirmedLows[]
  competitorSnapshot / selectedOwnSnapshot / alternativeOwnSnapshots
  combinationSignature / combinationLabel / differenceFen / reasons

missingOwnGroups[]
  combinationSignature / combinationLabel / missingReason
  earliestRank / minimumConfirmedPayableFen
  shops[] / offers[]

reviewRows[]
  snapshot / reasons / positions[]
```

每个 SKU 行至少返回：店铺、商品标题、完整链接、全部搜索排名、SKU 文本、结构化部件、库存、活动、价格置信度、预计到手价、组合状态、对应我方 SKU、差价和判断原因。

聚合必须在服务端完成，前端不自行推断组合状态或重新计算价格。重复搜索位置不可因按店铺分组而丢失。

## 13. 报告界面

运行详情页顶部显示：

- 搜索完成度，例如 `50/50` 或 `37/50，平台验证暂停`。
- 店铺数、唯一商品数、SKU 数。
- 确认低价数、我方缺失组合数、人工复核数和采集异常数。
- 我方已配置链接数、成功采集数和基准完整性状态。

主体固定为三个业务区：

### 13.1 前 50 价盘

- 以店铺为一级分组，默认按最早排名排序。
- 店铺行显示排名范围、商品数、SKU 数、最低确认价、低价数和缺失组合数。
- 展开后显示每个商品和每个 SKU 的价格、活动、库存、组合、我方对应价格、差价与链接。
- 支持按店铺、排名、组合状态、库存和价格置信度筛选。

### 13.2 确认低价同行

- 只显示 `MATCHED` 且满足低价表达式的行。
- 默认按差价从大到小、最早排名从小到大排序。
- 同时显示选中的我方最低基准及其他我方同组合链接，避免运营误解基准来源。

### 13.3 我方缺失组合

- 每个组合签名只显示一个摘要组。
- 组内显示相同组合的同行店铺、最低确认价、首次排名、全部链接和库存。
- 明确标注“无同组合我方基准，不属于低价告警”。
- `OWN_OUT_OF_STOCK_ONLY` 单独标注“我方有组合但无库存”。

现有逐 SKU 审计表继续保留在页面下方，供查看原始活动、证据和排除原因。桌面端允许表格横向滚动；窄屏使用固定列宽和横向滚动，不压缩到文字重叠或裁切链接。

## 14. 企业微信通知

每个运行最多发送一条业务摘要，内容包括：

- 型号、检查时间和前 50 完成度。
- 扫描位置数、店铺数、商品数和 SKU 数。
- 确认低价数、我方缺失组合数、人工复核数和异常数。
- 差价最大的前 10 条确认低价，包含店铺、排名、组合、同行价、我方价、差价和链接。
- 最低价优先的前 10 个我方缺失组合，包含组合、店铺数、最低价、首次排名和代表链接。
- 完整运行报告入口。

通知由 `RunAlertNotificationBatch` 幂等发送。数据库先保存报告和告警，再尝试企业微信；通知失败不能丢失结果。首次真实发送前必须在页面生成预览，并由用户在当次操作中再次确认；在获得该确认前只允许预览或测试模式，不向运营群发送。

系统永远不在企业微信或后台自动执行改价，只向运营提供人工判断依据。

## 15. Mac 辅助功能树修复

当前自动采集助手可能在序列化整个淘宝应用辅助功能树时触发 `TREE_LIMIT_REACHED`。修复必须缩小读取根节点，而不是无限提高全局节点上限：

1. 优先使用 `AXFocusedWindow`，不可用时回退到 `AXMainWindow`。
2. 每次读取和动作定位都从当前窗口的新鲜根节点开始，避免沿用页面切换前的失效路径。
3. 优先遍历可见、可交互子树；仅在定位目标需要时展开滚动区域的子节点。
4. 默认保护上限为 4,000 个节点、深度 28、单次 6 秒和序列化结果 8 MiB，均通过内部配置集中管理。
5. 达到任一限制时返回带根窗口、已访问节点数、深度和耗时的类型化错误，不提交截断树作为成功结果。
6. 登录框、验证码或平台验证被识别后立即暂停，等待人工处理，不尝试自动绕过。

动作执行后的验证也必须限制在同一个当前窗口范围。修复后仍无法读取页面时，运行进入 `PARTIAL_FAILED` 或对应暂停状态，并保存脱敏诊断证据。

## 16. 错误与降级规则

- 登录失效：`PAUSED_LOGIN`，不继续点击。
- 验证码或平台挑战：`PAUSED_CHALLENGE`，不绕过。
- 少于 50 个位置且无结束标记：运行不得标为 `SUCCEEDED`。
- 某商品全 SKU 未遍历完整：标记 `SKU_ENUMERATION_INCOMPLETE`，相关结果进入复核。
- SKU 部件、型号、数量或价格不完整：`REVIEW`，不告警。
- 价格在稳定等待期内持续变化：`PRICE_UNSTABLE`，保存读数与截图，不告警。
- 我方任一启用链接失败：缺失组合判断降级为 `OWN_CATALOG_INCOMPLETE` 复核。
- 商品详情重复采集：按运行、商品、SKU 和证据摘要幂等写入，不产生重复行。
- 企业微信失败：保留 `PENDING` 或 `FAILED` 批次，按既定退避重试，不重新创建业务结果。

任何部分失败都要显示已读位置、已抓商品、已抓 SKU、失败数和未完成数。系统不能把部分数据包装成完整价盘。

## 17. 数据与安全

- 淘宝登录状态只存在于用户安装的桌面版，不进入项目数据库和日志。
- 企业微信 Webhook 由服务端加密保存，不进入采集器、前端、Git、导出表或截图。
- 公开 GitHub 仓库只提交模拟数据和脱敏证据。
- 截图和辅助功能快照默认保存在本地受控目录，账号名、令牌和本机路径在日志中脱敏。
- 所有外部链接只用于运营人工打开核对，系统不在后台模拟购买、下单或支付。
- 采集频率和交互节奏保持可配置；遇到平台限制立即暂停，不通过切换账号、代理或其他方式规避。

## 18. 历史数据迁移

- 新字段均为可空，数据库迁移不强制回填旧 `OfferSnapshot`。
- 旧运行在页面标记为“历史规则，未计算组合签名”，继续显示已有逐 SKU 结果。
- 不对历史运行补发低价告警或企业微信通知。
- 新规则上线后的运行必须写入 `combinationState` 和规则版本；出现空状态即视为评价未完成。
- 旧的单一我方基准仍可供旧接口读取，但新报告和告警只使用逐组合 `comparisonOwnSnapshotId`。

## 19. 测试策略

### 19.1 单元测试

- 相同部件不同输入顺序生成相同签名。
- 品牌和型号别名规范化后生成相同签名。
- 成色、核心数量或付费配件不同会生成不同签名。
- 赠品和服务变化不改变签名。
- `colorComparable` 开启和关闭分别符合颜色规则。
- `UNKNOWN` 部件、缺少数量或模糊型号进入 `REVIEW`。
- 同一组合多个我方 SKU 选择最低确认到手价，并按固定规则解决同价。
- 同行低 `1` 分产生告警，等价或更高不告警。
- 无我方签名产生 `MISSING_OWN` 且不创建 `PriceAlert`。
- 我方目录不完整时缺失结论降级为复核。

### 19.2 集成测试

- 50 个位置中重复商品只采集一次详情，但全部排名出现在报告。
- 数据库迁移、自关联和索引正常，删除基准快照时引用置空。
- 同一运行重复提交桌面报告不重复创建快照、告警或通知批次。
- 报告 API 的店铺、低价和缺失分组数量与原始快照一致。
- 通知失败重试时只发送一个批次。
- 旧运行没有组合字段时仍可打开页面。

### 19.3 前端测试

- 三个业务区的筛选、排序、展开和链接正确。
- 多排名、多个我方备选链接和活动明细均可查看。
- 桌面与窄屏下表格不重叠、不裁切，横向滚动稳定。
- 空结果、部分失败、暂停登录和历史运行状态有明确展示。

### 19.4 真实验收顺序

1. 在当前淘宝桌面版窗口验证聚焦窗口子树读取，确认不再因整棵应用树触发 `TREE_LIMIT_REACHED`。
2. 分别对 `Sony MDR-7506` 和 `RODE NT1S` 采集前 3 个搜索位置，核对每个商品全部可见 SKU、活动价、库存和组合角色。
3. 验证规则示例：同配置 `589` 元对我方 `610` 元应显示低 `21` 元；同价 `1480` 元不告警；错误型号 `NT1` 即使为 `1385` 元也应排除。示例价格只用于验收规则，不作为固定市场价格。
4. 两个型号分别执行完整前 50 位置，检查结束标记、重复位置、店铺分组和 SKU 完整率。
5. 先生成企业微信预览；用户再次确认后只发送一条真实测试消息，核对摘要、前 10 和报告链接。

## 20. 完成标准

本功能只有同时满足以下条件才可标记完成：

- 前 50 个位置定义、结束条件和重复位置保留通过测试。
- 当前淘宝桌面版可在受限窗口子树下稳定读取，不再依赖整棵应用树。
- 每个可访问商品的全部有效 SKU、活动、库存和证据可追溯。
- 每条 `MATCHED` 同行 SKU 都能指向实际采用的我方最低价快照。
- 不同组合、错误型号、未知配置和不确定价格不会产生低价告警。
- “前 50 价盘”“确认低价同行”“我方缺失组合”三类报告与原始数据一致。
- 企业微信按运行最多发送一条摘要，并且首次真实发送经过当次人工确认。
- Mac 与 Windows 共享相同合同和业务判断；平台差异只位于桌面驱动层。
- 全流程只监控、报告和提醒，不自动修改任何店铺价格。
